# Niven project data and schema

## Implemented data stores

| Data | Current system of record | Project usage |
| --- | --- | --- |
| RSVP submissions and totals | Google Forms response sheet | Form submissions use the public Form endpoint; server routes read the published CSV. No RSVP records are stored in Supabase by this app. |
| Guestbook messages | Google Forms response sheet and Supabase `public.guestbook` | Public guestbook combines non-empty form response messages with approved Supabase entries. New guestbook-form submissions are stored in Supabase; RSVP form messages remain in the sheet. |
| Invitation photos and music | Files in `public/` | Served as static assets; not Supabase Storage. |

## Guestbook table

The app expects this compatible schema. Confirm it against the actual source and target databases before transferring records; the hosted schema has not been inspected in this task.

| Column | Type | Constraints / behavior |
| --- | --- | --- |
| `id` | `uuid` | Primary key; generated by `gen_random_uuid()` |
| `name` | `text` | Required; API trims and limits to 80 Unicode code points |
| `message` | `text` | Required; API trims and limits to 500 Unicode code points |
| `edit_token` | `uuid` | Required; generated by default; returned only to the creating guest and used to authorize edits |
| `approved` | `boolean` | Required; default `true`; public list only returns approved entries |
| `created_at` | `timestamptz` | Required; default `now()` |

There are no application-declared foreign keys or indexes beyond the primary key. The API uses the server-side Supabase service-role key, which bypasses Row Level Security (RLS). The shared-database SQL enables RLS and revokes direct `anon`/`authenticated` table privileges while granting the backend `service_role` access.

## Data-transfer implications

- The shared Supabase SQL creates the guestbook table; it does not copy rows from another project. Google Form messages remain in the response sheet and are fetched at runtime, not imported to Supabase. `/admin` displays RSVP sheet rows alongside guestbook administration.
- For an existing guestbook, copy `id`, `name`, `message`, `edit_token`, `approved`, and `created_at` after confirming both schemas. Preserving IDs and edit tokens keeps existing browser edit credentials valid; changing tokens will prevent old clients from editing their entries.
- Check for duplicate IDs and any table rows not matching this schema before import. Back up the source and target first. Validate counts and a few non-sensitive records after the copy.
- RSVP data stays in Google Forms/Sheets unless the product is explicitly changed. Do not import those responses into Supabase as part of a guestbook transfer.
- Current project code stores uploaded media as local public assets, so there are no Niven Supabase Storage objects to migrate based on the checked-in implementation. Other apps using the shared database may have separate buckets and data-transfer needs.

## Shared Supabase artifacts

`supabase/shared/002_add_to_existing_northstar.sql` is the prepared additive setup for the existing Northstar database. `001_bootstrap_empty.sql` is for a truly empty destination only. `inspect_destination.sql` reads database metadata. These files are setup artifacts, not a migration history, and were not executed against Supabase as part of this documentation update. They do not move guestbook records, Auth users, Storage objects, or settings from another project.
